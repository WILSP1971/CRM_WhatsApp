> ## ⚠️ NOTA DE REVISIÓN POST-APROBACIÓN (2026-10-04 — trazabilidad C8)
> Esta SPEC fue **aprobada originalmente** (bloque PLAN-012 F3) con un diseño de **"descargar + cifrar la media de Instagram"** espejando `whatsapp/media_client.py` + `audio_store.py` (ADR-009), con un PASO 0 bloqueante para confirmar el host del CDN y un gatillo condicional para crear ADR-017. **Una investigación posterior a su redacción encontró un hallazgo que cambia el diseño**, y el **Lead tomó una decisión vinculante** al respecto. Esta es una **REVISIÓN de diseño motivada por nueva información**, NO una SPEC nueva (conserva ID y estado `APROBADA`); el cambio es *reductor de alcance y de riesgo* (menos egress, menos superficie, menos código), por eso no requiere re-aprobación completa — pero se deja trazado aquí.
>
> **Hallazgo (investigación propia, con fuentes cruzadas de producción):**
> 1. **El host del CDN SÍ quedó identificado**: la media de los DMs de Instagram se sirve desde `lookaside.fbsbx.com` (patrón `https://lookaside.fbsbx.com/ig_messaging_cdn/?asset_id=...&signature=...`), distinto de `graph.facebook.com`. Meta **NO** publica este host como contrato literal (usa placeholders `"CDN-URL"`/`"<ATTACHMENT_URL>"` en su doc de webhook de mensajes); el host se confirma por **evidencia cruzada de integraciones de producción independientes** (CM.com, comunidad ManyChat, issue de Chatwoot, herramientas públicas) — NO es un contrato estable comprometido por Meta.
> 2. **Hallazgo CRÍTICO (el que obliga al rediseño):** la política de plataforma de Meta para Instagram Messaging **prohíbe descargar/retener/cachear** el contenido multimedia de los DMs. Evidencia directa: rechazo REAL de Meta App Review a Chatwoot (`github.com/chatwoot/chatwoot/issues/8583`) citando textualmente *"Proper handling of media CDN URLs by not storing/caching the media content"*. La guía esperada de Meta: la app **SOLO** guarda la URL del CDN ("privacy-aware CDN URL") del payload del webhook y la usa para **renderizar bajo demanda** — nunca descarga el binario a almacenamiento propio. La URL deja de resolver cuando Instagram expira/borra el contenido (control de Meta, por diseño).
> 3. **Distinto de WhatsApp:** la Cloud API de WhatsApp SÍ permite/requiere descargar el binario (URLs temporales que expiran en minutos; flujo `media_id → URL temporal → GET binario`) — por eso `media_client.py`/`audio_store.py` (ADR-009) existen y son correctos **PARA WHATSAPP**. Instagram es un contrato de producto DIFERENTE: su URL de CDN (también temporal/firmada) está pensada para usarse **directamente como fuente de renderizado** (`<img src="...">` / fetch bajo demanda desde el cliente), no para descargarse y persistirse en el backend.
>
> **DECISIÓN VINCULANTE DEL LEAD (ya tomada, NO SE REABRE):** *"Solo guardar la URL del CDN (Recomendado)"* — descripción exacta aprobada: *"No se descarga ni cifra el binario. Se persiste la URL firmada del CDN (`lookaside.fbsbx.com`) tal como la entrega Meta, y el agente humano la abre/renderiza bajo demanda desde la Bandeja. Evita el riesgo de rechazo de App Review documentado; mucho más simple (sin `audio_store`/cifrado nuevo). Riesgo: la URL expira/se revoca si el usuario borra el contenido (igual que la política de Meta exige)."*

## Objetivo

**Persistir la REFERENCIA a la media** de los DMs de Instagram — la **URL firmada del CDN de Meta** (`lookaside.fbsbx.com`, tal como la entrega el payload del webhook) y su `type` — para que el **agente humano la abra/renderice bajo demanda desde la Bandeja**, **SIN descargar ni cifrar el binario** y **SIN ningún egress de backend hacia el CDN de media**. Esto cumple la política de Meta ("not storing/caching the media content", `chatwoot#8583`) y la decisión vinculante del Lead ("Solo guardar la URL del CDN"). Es una SPEC de **datos + enganche de persistencia**, *no* de transporte: el backend nunca abre una conexión saliente para la media.

## Contexto

Verificado en el repo (fuente de verdad — 2026-10-04):
- **El parser de SPEC-086 ya entrega lo necesario:** `InstagramMessageEvent(..., attachments)` donde `attachments` es una lista de `{type, url}` extraída de `message.attachments[].payload.url` del payload de Meta. La URL es la **URL firmada del CDN** que Meta espera que se use directamente — no requiere resolución de `media_id` (a diferencia de WhatsApp).
- **El worker de SPEC-087 ya persiste el `Message` bajo RLS** y, por el diseño original, encolaba los `attachments` en una cola Redis `ig:media_pending` pensada para una "descarga futura" por esta SPEC-088. Con el diseño vigente **no hay descarga**, así que esa cola deja de tener consumidor útil (ver §"Implicación de la cola").
- **`messages` NO tiene hoy un campo para una URL de media EXTERNA.** `Message.audio_ref` (SPEC-054/058) es una **referencia OPACA a un blob cifrado LOCAL** (`audio_store`, ADR-009) de las notas de voz de WhatsApp — su semántica es "apunta a un binario que el backend descargó y cifró en reposo". **Reutilizarlo para una URL externa de Meta sería un error semántico**: no es opaco, no es local, no está cifrado, y su ciclo de vida lo controla Meta (expira), no el job de retención de SPEC-041/058. Por eso esta SPEC añade una **columna aditiva dedicada** para la referencia de media externa (ver §Alcance IN), dejando `audio_ref` EXCLUSIVAMENTE para su uso actual de WhatsApp.
- **`whatsapp/media_client.py` + `audio_store.py` (ADR-009) son el patrón CORRECTO para WhatsApp** y NO se tocan ni se extienden a Instagram (ver §"ADR-009" en Notas de seguridad). La URL de WhatsApp expira en minutos y obliga a descargar; la de Instagram está pensada para consumo directo.
- **BLOQUEO DE META APP REVIEW (R-110):** la media se verifica con el simulador firmado (payloads con `attachments`) + cuentas de prueba; NO con media de usuarios reales hasta que Meta apruebe (Q1=B, DIFERIDO al Lead).

## Alcance

### IN
- **Columna aditiva en `messages` para la referencia de media externa de Instagram** (migración Alembic aditiva, no destructiva, espejo estructural de cómo se añadieron columnas en SPEC-054): un campo para la **URL del CDN tal cual** (`String`, nullable; longitud holgada, p.ej. `String(2048)`, porque la URL firmada de Meta incluye `asset_id`/`signature` largos) y reutilización del campo `tipo`/`mime_type` existente o un pequeño campo de `type` del attachment (`image`/`video`/`audio`/`file`, tal como lo clasifica Meta en `attachments[].type`). El implementador elige el nombre (sugerencia: `media_url` + reutilizar `mime_type` o añadir `media_type`); **debe documentar en el docstring del modelo** que esta columna es una **URL EXTERNA de Meta, NO cifrada, NO local, de ciclo de vida controlado por Meta (expira)**, explícitamente distinta de `audio_ref` (ADR-009). None para mensajes sin adjunto y para los de WhatsApp/webchat.
- **Persistencia de la referencia en el flujo del worker de SPEC-087:** al persistir un `Message` cuyo `event` trae `attachments`, el worker guarda la(s) URL(s) del CDN y su `type` tal cual llegan, **en el MISMO flujo síncrono** de persistencia del mensaje (sin pasar por la cola `ig:media_pending`, que queda obsoleta — ver §Implicación de la cola). Si un mensaje trae varios attachments, se persisten todos (contrato a definir con el implementador: columna única para el caso de 1 adjunto típico de DM, o tabla hija mínima si se requiere multiplicidad; **decisión de implementación acotada**, debe quedar documentada). Idempotencia: una reentrega del mismo `mid` (UNIQUE `wamid`, SPEC-085 §3.4) NO duplica el mensaje ni la referencia.
- **Validación de FORMA de la URL (defensa en profundidad, SIN abrir conexión):** antes de persistir, validar que la URL es sintácticamente una URL `https` **y que su host pertenece al CDN esperado de Meta** (host exacto `lookaside.fbsbx.com`, `scheme=https`, sin userinfo embebido). Esto es una **validación de cadena en memoria**, NO un egress: el backend **nunca** hace un GET a esa URL. Si la URL no supera la validación, se audita (metadatos, sin la URL con credenciales en claro) y **no se persiste la referencia** (el mensaje de texto, si lo hay, se persiste igual). Ver §"Decisión sobre egress" para por qué esto NO es egress ni requiere ADR.
- **Renderizado bajo demanda desde el CLIENTE:** la API de conversaciones (SPEC-087 ya persiste el mensaje; SPEC-090 ajusta la Bandeja) expone la URL del CDN al frontend autenticado del agente, y es el **navegador del agente** quien hace el fetch a `lookaside.fbsbx.com` para renderizar (`<img src="...">` o enlace "Abrir adjunto"). El backend solo **transporta la cadena de la URL** en su respuesta JSON — no el binario.

## Requisitos funcionales
- RF-01 Un `Message` cuyo `event` trae `attachments` persiste la **URL del CDN tal cual** + su `type` en la columna aditiva de `messages`, en el flujo síncrono del worker (SPEC-087), **sin descargar el binario**.
- RF-02 **CERO descarga y CERO egress de backend para media:** no existe `media_client.py` de IG; no hay ningún cliente HTTP del backend que haga un GET a `lookaside.fbsbx.com` ni a ningún host de CDN de media. El binario NUNCA toca el almacenamiento del backend.
- RF-03 **Validación de forma (sin conexión):** la URL se valida como `https` + host exacto `lookaside.fbsbx.com` + sin userinfo **en memoria** antes de persistir; una URL que no cumple se audita (metadatos) y **no** se persiste como referencia. Esta validación NO abre ninguna conexión.
- RF-04 Idempotencia: una reentrega del mismo `mid` NO duplica el mensaje ni la referencia de media (UNIQUE `wamid`, SPEC-085 §3.4).
- RF-05 **No reutilización de ADR-009/`audio_ref`:** la referencia de media de IG vive en una columna aditiva nueva, documentada como URL externa NO cifrada; `audio_ref`/`audio_store`/ADR-009 permanecen EXCLUSIVOS de las notas de voz de WhatsApp.
- RF-06 La URL del CDN se expone al frontend autenticado del agente para render bajo demanda **desde el cliente**; el backend transporta la cadena JSON, no el binario.
- RF-07 **Expiración aceptada:** cuando Meta expira/revoca la URL (p.ej. el usuario borró el contenido), el agente ve un error de carga del adjunto en la Bandeja; esto es comportamiento **ACEPTADO** (política de Meta), NO un bug; no se implementa refresco de URL (Meta no lo documenta — limitación conocida).

## Notas de ADR (decisión — PLAN-012 §11.2 RESUELTA)
- **ADR-017 NO se crea.** El gatillo condicional original ("crear ADR-017 si el host del CDN ≠ `graph.facebook.com`") **ya no aplica**, porque ese gatillo presuponía **egress de backend** hacia el CDN (descarga del binario). Bajo el diseño vigente **no hay egress de backend para media** (el único consumidor de la URL es el navegador del agente), por lo que **no hay borde de egress nuevo que acotar** y, por tanto, **no hay decisión arquitectónica de egress que registrar en un ADR**. Crear un ADR para "no hacemos egress" sería ruido. `next_adr` **NO se consume** (queda como está; esta SPEC no lo toca).
- **ADR-006 NO cambia.** Sigue cubriendo el egress de *envío* a `graph.facebook.com` (WhatsApp e Instagram, ampliado por SPEC-085, lo usa SPEC-089). La media entrante no añade egress de backend.
- **El ADR aplicable es, implícitamente, ADR-005 (la IA sin egress) reforzado:** esta SPEC no abre ninguna salida nueva; si acaso, *reduce* la superficie respecto del diseño original. No requiere ADR propio.

## Riesgos
- R-115' (**reinterpretado** — host del CDN / contrato de media): el host (`lookaside.fbsbx.com`) está identificado por evidencia cruzada de producción, pero Meta NO lo compromete como contrato estable. Mitigación: como el backend **no hace egress** al CDN, un cambio de host de Meta **no rompe un transporte de backend** — a lo sumo cambia la URL que Meta entrega en el payload, que se persiste igual tal cual llegue (la validación de forma usa el host observado `lookaside.fbsbx.com`; si Meta lo cambiara, se audita y la referencia podría no persistirse hasta ajustar el host esperado — ajuste de una sola cadena, sin tocar egress). El impacto de un cambio de Meta es MÍNIMO frente al diseño original (que habría roto una descarga y una allowlist de egress).
- R-115'' (**URL expira/se revoca** — aceptado por el Lead): cuando el usuario borra el contenido o Meta expira la URL, el agente ve un error de carga del adjunto en la Bandeja. **Comportamiento ACEPTADO, no un bug.** Meta no documenta un mecanismo oficial de refresco → **limitación conocida y aceptada**; no se implementa re-resolución.
- R-110 (bloqueo de Meta App Review — sigue vigente igual): verificación con simulador firmado (`attachments`) + cuentas de prueba; activación real diferida al Lead (C6).
- R-114 (egress mal extendido) — **mitigado por construcción**: no se extiende ninguna allowlist de egress de backend para media (no hay egress).
- R-117 (regresión de WhatsApp/STT): esta SPEC es aditiva (una columna + enganche de persistencia); no toca `media_client.py`/`audio_store`/STT de WhatsApp.
